# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

PersonalTube is a single-user, local-only web app: a personal YouTube front page that is on the viewer's side rather than YouTube's. The user's own queue comes first, suggestions are few and explained, and the player is built to end (see "Design stance"). Its video library is the HackerTube data export (videos recommended on Hacker News), but that is a silent backbone: the UI calls it "the library" and does not mention HN outside the attribution footer and the collapsed "What people said" section of a video.

## Commands

Dependencies are managed with pixi (`pixi.toml`, top-level table `[workspace]`).

```bash
pixi run start        # serve the app at http://127.0.0.1:8765
pixi run fetch-meta   # fetch/resume YouTube metadata into youtube_meta.jsonl (add --refresh to refetch all)
pixi run apk          # build the Android app: android/app/build/outputs/apk/debug/app-debug.apk
```

There are no tests or linter, and no build step outside `android/`. The frontend is plain files served from `static/`; reload the browser to see changes. The server reloads itself when a `.py` file changes (uvicorn `reload`, via watchfiles); it loads the dataset at import time, so each reload takes a few seconds.

The YouTube API key is read from `YOUTUBE_API_KEY`, falling back to the login keyring through `secret-tool` (`ytkey.py` has the store command). The app runs without a key; only following channels by URL, refreshing uploads and importing playlists need one.

## Architecture

Three layers of data, all keyed by the 11-character YouTube id `vid`:

1. **Read-only dataset** (`videos.jsonl`, `mentions.jsonl`, `related.jsonl`, `taxonomy.json`): loaded into module-level dicts at the top of `server.py` (`VIDEOS`, `V`, `MENTIONS`, `RELATED`, `BY_CHANNEL`, `BLOB`, `DUPES`). `embeddings.npy` is loaded with numpy as `EMB` (rows indexed by `EMB_ROW`) and used only for recommendations. Search is word matching, not embeddings: `relevance()` matches whole words and word beginnings against the per-video word sets in `WORDS` and ranks title over channel over topic and tags; `match()` extends it to the user's own videos from outside the library (`own_extra()`: uploads of followed channels, playlist entries, anything watched or rated), and `respell()` retries a search that found nothing with the closest known words (`difflib`), reported to the frontend as `corrected`.
2. **YouTube metadata cache** (`youtube_meta.jsonl`, gitignored, written by `fetch_youtube_meta.py`): raw `videos.list` items. `load_meta()` reduces them to `META` (duration, channel id, publish date, views, or `{"gone": True}`) and re-reads the file whenever its mtime changes, so endpoints call it first and a running fetch shows up without a restart.
3. **User state** (`state.db`, SQLite, gitignored): `watched`, `hidden`, `follows`, `playlists`/`items`, `kv`, `ratings` (1 liked, -1 disliked), `dearrow` and `ytsearch` (caches), `progress` (position of started, unfinished videos), `watchlog` (seconds actually played per day and video), `intents` (answers to "what are you here for?"), `topics` (area or category id to 1 "more of this" / -1 "less of this"), `descs` (YouTube descriptions of extras, fetched when a video is first opened), `sponsor` (a cache of SponsorBlock segments) and `extra`. `follows.quiet` marks a followed channel that is kept off the home page; `watched.src` and `ratings.src` are `'takeout'` for rows from a Takeout import, so `/api/takeout/forget` can take the import back. `extra` holds videos from outside the HN dataset (uploads of followed channels with `upload=1`, imported playlist entries, and YouTube search results). The schema is `SCHEMA` in `server.py`, created with `create table if not exists`; new columns need an explicit `alter table` migration next to it, as done for `extra.views`.

A video is therefore either an "HN video" (`vid in V`) or an "extra" (`vid in st.extra`), and code that handles a vid must cover both: `State` snapshots the user tables per request, `card(vid, st)` builds the JSON the frontend renders for either kind, and `passes()` applies the filters (extras have no topic, so they fail any area/category filter).

Recurring exclusion rules for HN videos, applied separately in each endpoint: `DUPES` (re-uploads, by normalised title), `META[vid]["gone"]`, hidden, and for the mix also `shelf_life == "news"` and `hn.recommenders == 0`.

`taste(st)` turns likes, dislikes and (weakly) watch history into a per-video affinity: the best rescaled embedding similarity to a liked video, a bonus for sharing HN recommenders (`RELATED`) or a channel with a like, and a penalty near dislikes. It is cached on the ratings/watched snapshot. `/api/foryou` ranks by it, and `build_mix()` multiplies its sampling weights by `exp(TASTE_PULL * affinity)`. Videos outside the HN data have no embedding, so they only count through their channel. Topic interests are applied on top, outside `taste()`: `topic_weight()` (a category's setting overrides its area's) multiplies mix weights through `topic_pull()`, lets For You list videos the taste model has no opinion on, and keeps "less of this" topics out of the branch-out picks. They are set with the plus/minus buttons on the Explore page and on topic pages (`topicCtl()`, `/api/topic`).

The on/off settings (`SETTINGS`, a dict of name to default: `hide_watched`, `dearrow`, `calm`, `ask_intent`, `sponsorblock`) live in `kv`, are read into `State` and reach the frontend as `B.settings`. Three settings are numbers: `home_max_len` (seconds, one of `HOME_MAX_LEN_CHOICES`, `B.home_max_len`), the length above which uploads of followed channels stay off the home page; `speed` (`SPEED_CHOICES`, `B.speed`), the speed every video starts at; and `dl_quality` (`DL_QUALITY_CHOICES`, `B.dl_quality`), the tallest picture a download may have. What SponsorBlock does with each category is `kv` key `sb:<category>` (skip, ask or off; defaults and colours in `SB_CATS`, `B.sb`). `calm` (frontend only) drops view counts and the "new" dots and badges; `ask_intent` turns on the question before the first video of a sitting. `hide_watched` is applied in each list endpoint (not history, liked or playlists). With `dearrow` on, `card()` attaches cached DeArrow data as `da`; the frontend asks `/api/dearrow` for the videos on screen that lack it and patches titles and frames in, falling back to YouTube's automatic frame (`mq2.jpg`) when DeArrow has none or its thumbnail service fails.

`build_mix()` builds the home page ("Home", `/api/mix`, rendered by `pageMix()`): `lead`, one pick drawn large as "Today's pick", and `items`, a single grid in this order: started videos (rows of `progress`), the next unwatched video of a few playlists (the "Watch later" one always among them), uploads from followed channels (not quiet ones, not over `home_max_len`), picks (score-weighted sampling with per-channel and per-area caps and weight boosts for followed channels and for taste) and a few "branch out" videos (ones the taste model does not lean towards, from the areas the user has watched least, one per area; none under a topic filter). There are no section headings; each card's `reason` badge says why it is there. On every page with filters the heading and the filter bar share one row (`filterBar()` with a `head`), Filters button on the right; pages carry no explanatory subtitle under their heading. It is deterministic for the day: every random draw is `rnd(seed, vid)`, a hash of (date, reshuffle count, vid), so state changes nudge the page instead of redealing it. Keep new randomness on that scheme rather than using `random`. Every suggestion carries a `reason` in personal terms.

## Design stance

The app should serve what the user came for and then let them go. Concretely, and to be kept when adding features:

- The home page is small and has an end; no infinite lists, no autoplay of a next video, nothing that plays without a click.
- The player (`startPlayer()` in `app.js`) has three backends behind one small interface (`time`, `dur`, `playing`, `seek`, `play`, `pause`, `destroy`), tried in this order: the phone's native player when `window.PTNative` exists (`nativeBackend()`), a downloaded file in a `<video>` (`fileBackend()`, when the card has `dl`), else YouTube's IFrame player (`ytBackend()`). A backend that fails hands over to the next. It asks once per sitting what the user came for (`intentGate()`, remembered three hours in `localStorage`, logged through `/api/intent`); hides the related list while a video plays; and on the end of a video destroys the player (so YouTube's end screen never shows) and renders `stopScreen()`: rate it, today's tally, the next video of the user's own playlist if there is one, "Done for now". After "just this video", a second video asks first.
- While playing it posts to `/api/progress/{vid}` every 15 seconds: the position (resume, "Continue watching") and the seconds actually played (today's tally, `/api/review` and the Review page). The native player does this itself in Kotlin, because the page may be asleep while it plays in the background.
- SponsorBlock (`/api/sponsor/{vid}`, `sb_lookup()`, looked up by hash prefix and cached a day in `sponsor`, nothing submitted): segments set to skip are skipped with an undo toast, those set to ask get a Skip button while they play, and a strip under the player shows where they are (`sponsorWatch()`). The native player does the same on its seek bar.
- Limits are nudges, by the user's choice: nothing is blocked inside the app.
- Wording stays plain and quiet: no counts or badges that ask for attention, no HN vocabulary.

"Watch later" is an ordinary playlist that the clock button on every card fills in one click (`/api/later/{vid}`, `later_id()`: the playlist remembered in `kv`, else the one named "Watch later", else a new one). The Save picker (`listPopup()`) ticks the playlists that hold the video and toggles membership.

Everything from Google Takeout comes in through one place, "Bring in your YouTube data" on Settings. The user drops or picks the export as it comes: the .zip (or the parts of a split one), its unzipped folder, or single files. `zipEntries()` in `app.js` reads a zip in place from its central directory (zip64 included) and inflates only `.csv`/`.json`/`.html` entries, kept to the YouTube folder when there is one. Each file goes up as the raw body of `/api/takeout/file` under one token; `/api/takeout/summary` says what they hold and `/api/takeout/import` brings in the parts left ticked. Files are told apart by shape, not name (names and headers are localised): a watch history is a JSON/HTML file in which `parse_history()` finds videos (names matching `TAKEOUT_SKIP`, such as search history, are not read); `subscriptions.csv` is a CSV whose rows hold a channel id next to its URL (`parse_subs()`); the rest are playlist CSVs read together by `parse_takeout()`, where a playlist row is a video id plus at most one more cell, and a playlist whose name starts with "Liked" (`is_likes()`) becomes likes. Watch marks and likes get `src='takeout'` so they can be taken back (`/api/takeout/forget`). Imported history rows are stored for every video, known or not, so code that counts or ranks watched videos must filter to `V` or `st.extra` first. Subscriptions need no API key, and channels found in the HN data (by channel id, through `CHAN_ID`) are followed under their HN name so their picks stay linked (`follow_subs()`).

Playlists arrive three ways: made here, imported by URL (`/api/playlists/import`, needs the key; a channel URL in the same box lists the channel's public playlists through `/api/playlists/channel` and imports the ticked ones one by one), or from Google Takeout through Settings (`import_playlists()`; same-named playlists are merged). Takeout needs no key, but videos outside the HN data then sit in `items` with no `extra` row ("pending") and stay invisible until a sync. `sync_playlist()` fills those in and, for playlists with a `yt_id`, three-way merges against `playlists.yt_seen` (the ids YouTube listed last time) so local additions and removals survive.

A search (`#/browse?q=`) also shows a "From YouTube" section under the first page of HN results: `ytResults()` asks `/api/ytsearch` after the page is drawn. `youtube_search()` spends 100 quota units per new query, so answers are cached in `ytsearch` for a day (`YT_SEARCH_FRESH`); results are stored as extras so they open and play in the app like any other video, minus live streams and clips under `MIN_UPLOAD_SECONDS`. `forget_old_searches()` deletes searches after 30 days together with the extras only they brought in (in no playlist, never watched, rated or hidden).

**Downloads**: a downloaded video is `DL_DIR/<vid>.mp4` (`downloads/`, or `PT_DOWNLOADS`; gitignored and kept out of Syncthing, so each device downloads for itself) beside `<vid>.json` (title, channel, length, height). `downloaded()` lists the files and `card()` marks them `dl`; `/media/{vid}.mp4` serves them with byte ranges (`?save=1` as an attachment). `POST /api/download/{vid}` starts a job, `DELETE` stops one or deletes the file, `/api/downloads` lists files and jobs. On the desktop the jobs are yt-dlp in one background thread (`dl_worker()`; ffmpeg joins picture and sound, deno answers YouTube's script challenges, all three from `pixi.toml`); on the phone `NATIVE` (set by `ptboot.py`) hands them to Kotlin (`Downloads.kt`). The frontend shows them on the video page (`dlPill()`), in the card menu and on the Library's Downloads tab (`renderDownloads()`), polling `/api/downloads` while a job runs; a removal waits out the toast's Undo before the file goes.

**Sync between devices** (`sync.py`, started from `server.py` as `SYNC`): `state.db` is per device and never shared. Triggers on the user's tables write every change to `sync_out`; every few seconds a thread appends those to `sync/<device id>.jsonl` (`SYNC_DIR`, gitignored, carried by Syncthing) and applies the other devices' files. Rows are settled by latest change (`sync_seen`); `watchlog` takes the larger number of seconds and `intents` are added once, so every line can be applied twice without harm. A file has one writer, so Syncthing never sees a conflict. The triggers are rebuilt from the table definitions at each start, so a new column is carried automatically, but a new table must be added to `TABLES` in `sync.py`. Caches (`dearrow`, `ytsearch`, `sponsor`) and the timers in `kv` are not shared; of `kv`, only the keys passed to `Sync(...)`. Playlist ids come from `new_pid()` (random), because a counter would hand out the same id on two devices. Code that should not be echoed to other devices has nothing to do: applying a remote change sets `sync_ctl.applying`, which silences the triggers.

**Android app** (`android/`): the pages are the web app's; only the player and downloads are native. `MainActivity.kt` starts a Python runtime (Chaquopy), `ptboot.py` imports `server.py` from the project folder that Syncthing keeps on the phone and serves it on the same `127.0.0.1:8765`, and a WebView shows it. The page reaches Kotlin through `window.PTNative` (`MainActivity.Bridge`: play, stop, seek, position, and the phone's own player settings, kept in SharedPreferences and shown under "On this phone" in Settings) and hears back through `window.ptNative('ended' | 'error', …)`. `NativePlayer.kt` is a ReVanced-style player in the app's look: NewPipeExtractor finds the streams (`Extractor.kt`, VISIONOS client, no PoToken) and Media3 plays them (`Playback.kt`: each stream as a one-stream DASH manifest, every googlevideo request a POST with `rn` and `range` in the address, as the NewPipe app does), in a 16:9 box above the page, fullscreen in landscape, in picture in picture, and on with the screen off through `PlaybackService` (a media session: notification and lock-screen controls). It has SponsorBlock on its seek bar, a quality and speed menu, sound only, double-tap seek and swipes for brightness and volume. When YouTube changes and extraction breaks, raise the NewPipeExtractor version in `build.gradle.kts`; meanwhile the page falls back to the IFrame player. The library, `static/` and `sync/` are read from that folder, so desktop changes reach the phone without a new build; the phone's own `state.db` is in app storage (`PT_STATE`). `.stignore` keeps the rest of the folder (`.pixi`, `.git`, `android/`, `state.db`, caches) off the phone; a new file the phone needs must not match it. Consequences: `server.py`, `sync.py` and `ytkey.py` must run on the phone's Python 3.12 with FastAPI 0.99 / pydantic 1 / numpy 1.26 (versions pinned in `android/app/build.gradle.kts`), and the frontend must work at phone width and by touch. The phone has no API key; uploads and details fetched on the desktop arrive through sync. Links that leave the origin open in the phone's browser, not in the WebView.

YouTube API calls go through `yt()`, which turns failures into `HTTPException`s whose `detail` the frontend shows in a toast. Upload refresh runs at most every 12 hours in a background thread triggered from `/api/mix`.

**Frontend** (`static/app.js`, no framework, no build): a hash router (`route()`) dispatching to `page*` functions that fetch from `/api/*` and set `#main` via template strings. Everything interpolated into HTML must go through `esc()`. `B` is the boot payload from `/api/boot` (sidebar, counts, taxonomy); Filters (`len`, `type`, `sort`, and `area` on the home page and For You) are per page and live in the hash query string (`#/browse?len=long&sort=gems`): `filterParams()` reads them, `filterBar()` renders the Filters button, active chips and collapsed panel as plain links, and nothing about them is stored. Topics have their own pages, `#/a/<area>` and `#/c/<category>`, reached from `#/explore` (the sidebar's Explore; `#/categories` still works) and rendered by `pageBrowse()` like `#/browse` and `#/channel/<name>`. History and Liked are the two tabs of `#/library` (`pageLibrary()`). Controls that need the YouTube API key are left out when there is none, rather than shown disabled; Settings is the one place that explains the key. Actions that remove something from view (hide, mark watched with "hide played" on, remove from a playlist, Watch later) pass an undo function to `toast()` rather than pointing at another page. `route()` sets the tab title (`pageTitle`, `TITLES`) and shows a thin bar when a page is slow; scroll positions are kept per history entry (`SCROLLS`, Navigation API) so Back returns to the same place. Keyboard shortcuts are one `keydown` handler (`GO`, `KEY_ACT`, `runAct()`), listed in the `#keys` dialog in `index.html`; keep the two in step. `localStorage` holds only theme, sidebar state and the current sitting's intent (`pt-intent`); resume positions are in `state.db`. Playback uses the YouTube IFrame API on the `youtube-nocookie.com` host.

## Constraints

- YouTube API data must not be redistributed: `youtube_meta.jsonl`, `state.db` and `sync/` stay gitignored, and the key never goes in a file.
- The server uses only the standard library plus FastAPI/uvicorn and numpy, and yt-dlp imported inside `ytdlp_download()` (desktop only: the phone has none); the fetch script is standard library only. Add new dependencies through `pixi.toml`.
- For DeArrow and SponsorBlock data, look videos up by hash prefix, and never submit to their APIs.
